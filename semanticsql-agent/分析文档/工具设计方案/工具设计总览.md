# SemanticSQL-Agent 统一三元组工具设计总览

## 1. 设计理念

### 1.1 核心原则
基于**统一三元组记忆架构**的革命性设计，所有工具采用智能化的**输入-输出接口**和**AI驱动的决策机制**：

- **统一接口**: 所有工具都使用 `run_with_triples(**params) -> TripleCollection` 接口
- **智能三元组驱动**: 输入和输出都基于增强的三元组集合（含置信度、时间戳、来源）
- **AI上下文感知**: 智能从memory获取相关上下文，支持语义查询和依赖分析
- **质量控制**: 内置置信度计算、重复检测和质量验证机制
- **即插即用**: 智能体可以动态调用任何工具并进行AI增强决策

### 1.2 增强架构统一性
```
每个工具的智能化标准流程：
第1步：智能输入 - 获取参数 + AI驱动的上下文获取 + 前置依赖验证
第2步：增强处理 - 基于上下文进行智能处理（含置信度计算、质量控制）
第3步：智能输出 - 生成高质量三元组集合，智能保存到memory并返回详细响应
```

## 2. 智能工具分类和职责

### 2.1 智能分析工具 (AI-Enhanced Analysis Tools) - 6个
**阶段定位**: 第一阶段，AI驱动的数据库和业务深度理解

| 工具名称 | 核心职责 | 智能特性 | 输入依赖 | 输出三元组类型 |
|---------|---------|---------|---------|---------------|
| schema_extraction | 智能数据库结构提取 | 自动类型推断、约束识别 | 数据库连接参数 | 表-列-类型增强三元组 |
| domain_analysis | AI业务领域识别 | 语义分析、领域分类 | schema结构 | 领域归属、业务概念、置信度 |
| field_analysis | 智能字段语义分析 | 上下文理解、语义推理 | schema + domain | 字段语义类型、业务角色 |
| column_analysis | AI列级深度分析 | 数据模式识别、业务含义推断 | 前序分析结果 | 列的业务含义、数据特征 |
| table_analysis | 智能表级业务逻辑 | 业务流程理解、角色识别 | 所有前序结果 | 表的业务角色、重要性评分 |
| er_analysis | AI实体关系分析 | 关系推理、依赖分析 | 所有分析结果 | 表间关系信息、关系强度 |

**智能执行顺序**: schema_extraction → domain_analysis → field_analysis → column_analysis → table_analysis → er_analysis
**依赖智能检查**: 每个工具执行前自动验证前置依赖的完整性和质量

### 2.2 智能生成工具 (AI-Driven Generation Tools) - 3个
**阶段定位**: 第二阶段，AI驱动的智能内容生成

| 工具名称 | 核心职责 | 智能特性 | 输入依赖 | 输出三元组类型 |
|---------|---------|---------|---------|---------------|
| scenario_operation | AI场景操作生成 | 业务理解、复杂度评估 | 所有分析结果 | 业务场景、操作类型、复杂度 |
| question_generation | 智能问题生成 | 语言优化、多样性保证 | 场景 + 分析结果 | 自然语言问题、难度评级 |
| sql_generation | AI SQL查询生成 | 意图理解、性能优化 | 问题 + 所有上下文 | SQL语句、查询信息、置信度 |

**智能执行顺序**: scenario_operation → question_generation → sql_generation（或直接 question → sql_generation）
**智能优化**: 基于历史成功率和用户反馈进行持续学习

### 2.3 智能验证工具 (AI-Enhanced Validation Tools) - 2个
**阶段定位**: 第三阶段，AI驱动的质量保证和安全执行

| 工具名称 | 核心职责 | 智能特性 | 输入依赖 | 输出三元组类型 |
|---------|---------|---------|---------|---------------|
| sql_validation | AI SQL语法逻辑验证 | 深度语法分析、逻辑推理 | SQL + schema信息 | 验证结果、错误信息、修复建议 |
| sql_execution | 智能SQL安全执行 | 性能预测、安全检查 | 验证通过的SQL | 执行结果、性能信息、优化建议 |

**智能执行顺序**: sql_validation → sql_execution
**安全保障**: 多层安全检查，防止恶意SQL和性能问题

### 2.4 AI反思工具 (AI-Powered Reflection Tools) - 1个
**阶段定位**: 第四阶段，AI驱动的质量评估和持续改进

| 工具名称 | 核心职责 | 智能特性 | 输入依赖 | 输出三元组类型 |
|---------|---------|---------|---------|---------------|
| sql_reflection | AI全流程质量评估 | 多维度评估、改进策略生成 | 所有阶段结果 | 质量分数、改进建议、学习反馈 |

**智能评估**: 基于多个维度（准确性、性能、可读性）进行综合评估

### 2.5 AI思考工具 (AI-Enhanced Thinking Tools) - 1个
**特殊定位**: 横跨所有阶段的AI增强工具

| 工具名称 | 核心职责 | 智能特性 | 输入依赖 | 输出三元组类型 |
|---------|---------|---------|---------|---------------|
| thinking_tool | AI智能思考增强 | 深度推理、上下文关联 | 任何工具的结果 + 全局上下文 | 增强后的三元组、推理路径 |

**AI增强**: 基于大语言模型的深度推理和上下文理解能力

### 3.3 增强输出格式规范
所有工具都返回增强的 `TripleCollection`，每个三元组包含：
- `subject`: 主体（表名、字段名、SQL等）
- `predicate`: 关系（has_column、generates_sql等）
- `object`: 客体（具体值、结构化数据等）
- `confidence`: 置信度（0.0-1.0）
- `timestamp`: 生成时间戳
- `source_tool`: 来源工具名称
- `metadata`: 额外元数据（推理路径、质量指标等）

## 4. 智能体调用模式

### 4.1 标准工作流
```python
# 完整的四阶段工作流
result = agent.execute_workflow(task="分析数据库并生成查询")

# 阶段包括：
# 1. Analysis Phase: 所有分析工具
# 2. Generation Phase: 场景、问题、SQL生成  
# 3. Validation Phase: 验证和执行
# 4. Reflection Phase: 质量评估
```

### 4.2 灵活调用
```python
# 单工具调用
result = agent.execute_tool("sql_generation", question="查询用户")

# 带思考增强的调用
result = agent.execute_tool_with_thinking("sql_generation", question="复杂查询")

# 阶段调用
result = agent.execute_phase("analysis", database_config=config)
```

### 4.3 思考增强决策
智能体根据以下条件动态决定是否使用ThinkingTool：
- **结果质量**: 三元组数量、内容丰富度
- **任务复杂度**: 参数复杂性、涉及表数量
- **上下文丰富度**: 可用三元组数量
- **历史经验**: 类似任务的成功率

## 6. 关键设计决策

### 6.1 为什么选择三元组架构？
- **统一性**: 所有数据都用相同格式存储和传递
- **灵活性**: 可以表达任意复杂的关系和结构
- **扩展性**: 新工具只需遵循三元组格式即可集成
- **性能**: 避免复杂的数据格式转换

### 6.2 为什么采用内部处理模式？
- **记忆纯净**: 只存储最终的结构化结果
- **处理灵活**: 每个工具可以用最适合的方式处理数据
- **性能优化**: 临时数据不持久化，减少内存占用

### 6.3 为什么智能体控制思考增强？
- **动态决策**: 根据实际情况决定是否需要增强
- **透明替换**: 增强结果直接替换原结果
- **即插即用**: 无需修改现有工具代码
